## 1. 目的和范围

用 F1 冻结后的一份真实时序报告，考察 AI 能不能把一条时序路径讲对、讲清楚。AI 说的每一个关键判断，都在**同一网表、同一分析配置**下用工具重查。最后形成文章 1，标题暂定《AI 如何解释这条时序路径：我用工具核对了它的每个关键判断》。

**不在范围内的：**
- 让 AI 修改 RTL，这属于阶段 B。AI 提出的修改建议只做记录。
- 修改任何评估文件。F1 冻结的 14 个文件一概不动；本流程新增的脚本和运行目录，按合同第 8 节属于"增加新的运行"，不算评估修订。
- 比较模型的一般能力。三个模型各做一次，结论只描述这一次。

## 5. 第 5–6 步：被测对象的诊断（执行计划第 3 步）

### 5.1 统一的运行外壳

三个模型都经过命令行版 Claude Code（运行时记录版本号）调用，**只换模型，不换外壳**。

- 每次运行都清空从桌面会话继承来的全部 `ANTHROPIC_*`、`CLAUDE*` 环境变量。
- 用 `--settings C:\Users\haoya\.diag-models\<模型>.json` 指定这次的接入地址和模型。这些文件在项目外，密钥由作者填写，操作者不读。
- 运行参数（三个模型完全相同）：`-p --tools "" --system-prompt <统一系统提示> --setting-sources project --strict-mcp-config --no-session-persistence --effort high --output-format stream-json --verbose`，再加上各自的 `--model`。
- 工作目录：项目外的一个新目录 `D:\study\diag_sandbox\<运行编号>\`，目录里不放任何文件，目录名不带提示信息。
- 不用全局切换工具。作者的 CC Switch 保持在 Claude 官方。

**2026-10-10 冒烟测试的结论**（原始输出在 `D:\study\diag_sandbox\smoke-20261010\`，不进 git）：
- 三个模型实际答题的分别是 `claude-opus-5-5`、`k3`、`deepseek-v4-pro`；
- 工具列表都为空，MCP 都为空；
- 没有加载用户设置里的钩子和插件，只有两个内置插件；
- 系统提示里的暗号三个模型都答对了。

**已知的残留差异**（文章中如实写出）：
1. Claude Code 在替换后的系统提示前，仍会加一句"基于 Claude Agent SDK 的 agent"一类的身份声明，三个模型都收到了；
2. 三个模型都收到同一段环境信息：工作目录、平台、日期；
3. 只有 Claude 那一次，因为是订阅登录，会额外收到一条带账号邮箱的提醒；
4. 思考功能三个模型都开启了，`--effort high` 在各家服务端如何生效无法核实；
5. Kimi 和 DeepSeek 经过各自的兼容层转换，Claude Code 会对这两个模型名给出"无法识别的模型"警告，并且只给出估算费用；
6. 冒烟测试中 DeepSeek 发生过一次自动重试。

### 5.3 题目和记录

- **系统提示**（三个模型相同）：说明身份是"被测试的时序分析助手"，只能依据所给材料作答，不确定就写不确定，引用证据要写"文件名:行号"。
- **题目**按执行计划第 3 步，要求写五部分：
  1. 报告事实，每条注明证据位置；
  2. 原因假设，要能被证伪；
  3. 缺失的证据；
  4. 下一步查询，尽量写成具体的 OpenSTA 命令；
  5. 可能的修改，不能靠放宽约束。
- **每次运行保存以下内容**：
  - 完整的命令行（配置文件只记路径）、CLI 版本、开始和结束时间；
  - 原始 stream-json，包括 init 记录（模型、工具、插件）和 result 记录；
  - 最终答复的原文。
- **运行核查**：从 init 和 result 记录中核对模型名，确认工具为空，确认没有加载 MCP 和用户插件；不符合时，这次运行作废，并保留作废记录。
- **介入日志** `diag/interventions.md`：按 assisted 模式，记录每次人工介入的时间、类型（提供上下文、纠正、提示、否决、人工修改）、内容和耗时。第 2 轮交还查询结果，算一次"提供上下文"。
- **不保存为交付物的内容**：模型的内部思考（执行计划第 4 节）。原始 stream-json 中如果含有思考内容，只放在备份里，不进 git，也不在文章中引用。

## 7. 第 8 步：工具重查和标签（执行计划第 4 步）

### 7.1 重查环境

- 新写一个 OpenSTA 查询脚本 `diag/scripts/diag_sta.tcl`，按 F1 的顺序重建分析：读库，link F1 运行冻结的网表 `runs/20261009-092827-base-T27.91/synth/netlist.v`，建 6 个 std scene，之后再施加 SDC（T = 27.91、C_load = 0.0024，TOOL-012），然后执行一份查询清单。
- **自检**：用这套环境复算六个点的最差 setup 和最小 hold，结果必须和 F1 运行 `sta/sta_results.tsv` 的 `WS` 行逐位相同。不相同就停下查明原因，不能用这套环境下任何结论。
- 每次查询都放在一个新的运行目录 `runs/<时间>-diag-<编号>/` 下，保存脚本、查询清单、完整日志和原始输出，日志按 `logcheck` 的规则检查。结束后复制到 `diag/queries/` 并生成 `SHA256SUMS`。

### 7.2 基础核对

基础核对是在看到任何 AI 输出之前定下的一组固定查询，只用于打标签，不交给被测对象。具体命令在实现计划里写定：
- 最差路径的完整报告，带 slew、电容、扇出和输入引脚；
- 同一 scene 下排名前若干条的路径，用来确认最差路径是否唯一；
- 最差路径上每个线网的扇出和负载；
- `check_setup`，检查有没有未约束的端点；
- 各 corner、各路径类别的最差路径。

### 7.3 标签规则

| 类型 | 核对方法 | 标签 |
|---|---|---|
| 事实 | 对照参考答案、报告原文和重查的原始输出 | **证实**、**推翻**、**无法核对**。工具报错、查询返回空、查错了路径，都不算证实（执行计划第 4 节验收 1） |
| 假设 | 设计一个能区分对错的查询来跑 | **支持**、**反对**、**未判定**（未判定要写明原因）。不能因为说得有道理就标为支持 |
| 证据引用 | 核对它写的文件名和行号 | **引用正确**、**引用错误** |
| 缺失证据、查询 | 判断是否可在冻结模型内回答，并实际执行 | **可执行**（附结果）、**模型外**（例如需要布局或寄生信息） |
| 修改建议 | 不验证 | **留给阶段 B** |

- 数值相同的标准：在报告给出的精度内一致。
- 每个标签都附上证据：重查命令和原始输出文件的位置。
- 标签由操作者提出，作者复核；双方有分歧时，两种意见都写进记录。

## 8. 第 9 步：第 2 轮

- 每个模型只拿回**它自己**第 1 轮提的查询的原始结果。操作者把这些查询翻译成 OpenSTA 命令，翻译过程记入介入日志；无法照原意执行的，注明原因，并把"无法执行"作为结果交还。
- 第 2 轮的题目由以下内容拼成：第 1 轮的系统提示和题目、它自己第 1 轮答复的原文、查询结果。最后只加一句"根据这些结果，确认或修正你第 1 轮的判断"。使用新会话，参数与第 1 轮相同。
- 第 2 轮看不到：参考答案、标签、基础核对的结果、其他模型的输出。
- 第 2 轮单独统计四类情况：改对了、改错了、坚持原判断、新提出的判断。新提出的事实类判断，按第 7.3 节同样核对。重查标签以第 1 轮为准。
