## 2. 时序与交易规则

### 2.1 记号

- `R_n`：第 n 个上升沿。`F_n`：紧随 `R_n` 之后、先于 `R_(n+1)` 的下降沿。
- `I_n`：DUT 在 `R_n` 采样到的输入，记为 `rst[n]`、`valid[n]`、`a[n]`、`b[n]`。这里用方括号下标表示"第 n 个边沿采样到的值"，`rst[n]` 不是低有效复位 `rst_n`。
- `O_k`：TB 在 `F_(k−1)` 读到的输出（`out_valid`、`out_data`）。

在 `F_n` 这个时刻，TB **先**读取并检查当前输出（即 `O_(n+1)`），**再**驱动供 `R_(n+1)` 采样的下一拍输入。下降沿读数只是功能仿真的采样约定，不表示 STA 使用半周期路径。

### 2.2 延迟 L

延迟为 L 的实现：交易 `I_n` 在 `R_(n+L−1)` 之后形成寄存输出，在 `F_(n+L−1)` 被读到，记为 `O_(n+L)`。基线 L=1：输入经组合逻辑在 `R_n` 打入输出寄存器，在 `F_n` 被读到，即 `O_(n+1)`。

| | `R_n` | `R_(n+1)` … `R_(n+L−1)` | `F_(n+L−1)` |
|---|---|---|---|
| 输入 | DUT 采样 `I_n` | — | — |
| valid | 进入第 1 级 | 逐级传递 | — |
| 输出 | — | — | TB 读到 `O_(n+L)`：`out_valid=1`，`out_data = f(a[n], b[n])` |

### 2.3 期望值

- `O_k.valid = valid[k−L] AND（对所有 j ∈ [k−L, k−1]，rst[j] = 0）`。如果 `k−L` 早于第一个输入，期望 valid 为 0。
- 期望 valid 为 1 时，还要求 `O_k.data = f(a[k−L], b[k−L])`，f 的定义见第 3.1 节。
- 每个 `R_j` 上，同步复位的优先级高于接收新交易，并且清空所有在途的 valid。

几个边界情况：
- **L=1**：`O_(n+1).valid = valid[n] AND NOT rst[n]`。
- **复位恰好在 `R_(n+L−1)`**：交易 n 被清掉，`O_(n+L).valid` 必须为 0。
- **复位恰好在 `R_(n+L)`**：`O_(n+L)` 已经在之前的下降沿读完，这次复位不会追溯取消已经交付的输出，它影响的是之后的观测。

上面的公式已经隐含了以下要求：每拍都能接收新交易，没有停顿；气泡随数据一起流动；交易不能丢失、重复或乱序，也不能多出输出。

### 2.4 复位、初始化与 X/Z

- 数据寄存器可以不复位。期望 valid 为 0 的观测点，不检查 `out_data`。
- TB 在第一个采样边沿之前就把 `rst` 置为已知的 1，并至少保持 4 个上升沿。设第一个采样到 `rst=1` 的边沿为 `R_j`，从 `F_j` 开始，每个观测点都要检查。
- 每个观测点上，`out_valid` 必须是确定的 0 或 1（不能是 X 或 Z），并且与期望值严格一致。期望 valid 为 1 时，`out_data` 出现任何 X/Z 或数值不等，都判失败。必须用四态比较（例如 `!==`），不能用可能把 X 当成"条件不成立"的普通比较代替。
- 测试向量里的 `rst`、`in_valid` 以及有效交易的数据，都必须是已知值。本合同不要求 DUT 对未知输入给出有定义的结果。

### 2.5 L 的配置

- 每个实现的 L 写在 `config/impl.<name>.cfg` 里，TB 通过 plusarg 读入。每个实现的 L 固定，不随输入变化。
- L 缺失、不是整数、超出允许范围，或与已审阅过的配置不一致，都必须报错，不能静默使用默认值。允许范围在 F1 之前是 1–3，F1 之后是 1–L_max。
- 候选与基线只要求交易级等价，不要求逐周期等价。

## 3. 功能与验证

### 3.1 参考函数

1. 把每一路的 16 位比特模式解码为有符号整数：a_i、b_i ∈ [−32768, 32767]。
2. 用任意精度整数计算 s = Σ a_i·b_i。s 的范围是 [−4294836224, 4294967296]，需要 34 位有符号数才能表示。
3. y = clamp(s, −2^31, 2^31−1)。
4. 把 y 编码为 32 位二进制补码，再与 `out_data` 比较。

中间步骤不得截断，也不得提前饱和。参考模型要独立编写，不能照搬 RTL 的表达式。

### 3.2 参考模型与向量

- `ref/model.py`：只包含上面这个纯函数。
- `ref/gen_vectors.py`：按场景和种子生成逐拍向量，每一行对应一个上升沿，至少包含 `rst`、`in_valid`、四路 a、四路 b、该拍输入对应的期望 y，以及场景标签。同时输出一份清单，内容包括种子、场景参数，以及在给定 L 下"应当被比较的交易数"。
- "应当被比较的交易数"按整个测试来统计，包括输入向量段，以及第 3.5 节规定的全部收尾观测。生成清单时，要把向量读完之后至少 L 上限加 1 拍的 `rst=0`、`in_valid=0` 当作已知的尾部，纳入 valid/复位时间线。计入的交易是：向量中被接收、在交付之前没有被复位取消、应当在测试结束之前交付的全部交易，包括在收尾段才交付的交易。收尾段的气泡不算交易。覆盖统计采用相同的范围。
- Python 给出的交易数只用来做总量核对，不能代替 TB 的逐拍判断。具体文件格式在实现计划里规定。

### 3.3 测试场景

1. **符号边界**：各路取 −32768、−1、0、1、32767 的组合。
2. **饱和边界**：完整和恰好等于下面四个值，用下表的构造（lane 按 0..3 排列，外审时已用 Python 核对）：

| 完整和 | a | b |
|---|---|---|
| 2^31−1 | (−32768, −32768, −1, 0) | (−32768, −32768, 1, 0) |
| 2^31 | (−32768, −32768, 0, 0) | (−32768, −32768, 0, 0) |
| −2^31 | (−32768, −32768, −32768, 0) | (32767, 32767, 2, 0) |
| −2^31−1 | (−32768, −32768, −32768, −1) | (32767, 32767, 2, 1) |

   另外还要覆盖远超上、下界的饱和。
3. **抵消**：正负乘积相加为 0 或很小的值。
4. **连续 valid**：长串的连续有效交易。
5. **气泡**：随机分布的气泡，以及若干固定模式。
6. **复位**：要覆盖正常交易流中的单拍复位、多拍复位、`rst` 与 `in_valid` 同拍，以及复位之后恢复接收。针对每个实现的实际 L，分别覆盖以下三种情况：
   - `R_n` 上 `rst=1`，阻止该拍的交易被接收；
   - 在 `R_(n+m)`（m = 1..L−1）上复位，取消已接收、尚未交付的交易；
   - 在 `R_(n+L)` 上复位，不会追溯取消已经交付的交易。

   L=1 时 m = 1..L−1 是空集，第二种情况记为不适用。
7. **随机**：均匀分布，以及偏向极值的分布。种子写入日志。

### 3.4 覆盖统计

覆盖统计要区分四类交易：生成的、被接收的、因复位取消的、实际被检查的。具体要求：
- 第 3.3 节第 2 条的四个精确边界，以及正、负两个方向的饱和，都必须由满足以下全部条件的交易命中：`in_valid=1`、`rst=0`、没有被后续复位取消、最终确实被比较过。
- 是否饱和，按原始完整和是否严格超出输出范围来判定，不能按饱和后的值或场景标签来计数。
- 连续 valid 和固定气泡模式，检查实际序列确实具有这些性质。
- 复位覆盖按被清空的在途交易及其位置、以及复位后的 valid 行为来统计，不要求被取消的交易产生输出。

各项计数按它的含义和实际的 L 来判定：
- 所有适用的必测场景和边界都必须命中。明确不适用的项不要求计数大于 0，但必须记录不适用的原因。
- "复位同拍、未被接收"和"已接收、后来被复位取消"要分开统计。L=1 时后一种的计数应当为 0，不能因此判覆盖失败。
- 精确边界、双向饱和这类需要交付数据的场景，仍然必须由实际被比较过的交易命中。

### 3.5 TB 行为

- 每个观测点都按第 2.3 节算出期望 valid，并与 DUT 的输出比较；不论 DUT 的 `out_valid` 是什么，都要比较。期望 valid 为 1 时，再比较数据。
- **收尾**：向量读完之后，保持 `rst=0`、`in_valid=0`，再运行至少 L 上限加 1 拍（F1 之前取 4 拍），并继续逐拍检查。这一段既要等所有应交付的交易排空，也要检查有没有多出的 valid。不得用最后一次复位清掉尚未交付的交易来结束测试。
- **必须判为失败的情况**：文件打不开、某一行解析失败、提前结束、L 不合法、检查数为零、超时。TB 要设一个有限的 watchdog。
- **通过的条件**：所有逐拍检查和收尾检查都完成，检查过的交易数 n 大于 0，并且等于 Python 给出的期望数。只有满足这些，才输出唯一一行 `SIM PASS checked=<n>` 并正常退出；否则输出 `SIM FAIL <原因>`，并以非 0 状态退出（例如调用 `$fatal`）。
- 仿真器使用 Icarus Verilog，版本见 `env/INSTALL_RECORD.md`，每次运行都记录版本。
- **门级功能仿真（必做）**：交给 STA 的那一份综合网表，要用相同的 L 配置、输入向量和逐拍判定规则再跑一次功能仿真，并记录网表的哈希，以确认两个流程用的是同一份产物。通过只说明这份网表在这组测试下与参考模型一致，不构成形式等价证明，也不是完整的功能证明。
  - 单元模型用固定来源的 `primitives.v` 和 `sky130_fd_sc_hd.v`，记录两个文件的哈希、编译宏和仿真命令。编译宏为 `-DFUNCTIONAL -DUNIT_DELAY=#1`，不回标 SDF，也不启用其他时序注释。
  - 在当前模型下，组合单元没有显式的传播延迟；本设计会用到的触发器（如 `dfxtp`），其 UDP 带 1 ns 的单位延迟。并不是所有时序单元都有这个延迟，例如锁存器 `dlxtp_1` 就没有，不能把这条说明推广到所有锁存器。
  - 对于本合同这种上升沿寄存器结构，功能仿真的时钟周期可以独立于 STA 的 T 选取。实现计划要固定仿真的 timescale、周期，以及驱动和观测的时刻，确保实际仿真的半周期严格大于 1 ns，并留出明确的余量，例如周期 10 ns、半周期 5 ns。这个周期只是为了让功能测试可靠执行，不验证 STA 的目标周期，也不验证 setup/hold；单位延迟仿真不提供实际单元延迟或物理时序方面的结论。模型或编译选项改变时，要重新核对这个前提。

### 3.6 TB 自检（F0 之后、F1 之前完成）

以下两次故意注错都必须让 TB 报错，退出码非 0：
- **数值错误**：例如某一路按无符号数处理，或饱和边界差 1。必须证明这个错误在被检查的交易中确实被触发了，比如那一路在检查过的交易里出现过负数。
- **valid 错位**：用一个变异 DUT，让 `out_valid` 相对正确时刻晚一拍，cfg 里的 L 保持不变。所用向量必须包含不恒定的 valid、复位边界和收尾段。不能用"把 cfg 的 L 改到允许范围之外"来做这项测试，因为那样被拒绝的是配置校验，并没有检验到 checker 本身。

自检结果作为证据保存。F1 之前按 L 为 1–3 做的自检，如果 F1 定下的 L_max 更小，这些自检作为历史证据仍然有效；但它们不授权候选使用超出 L_max 的 L。正式回归必须用最终的 1..L_max 范围校验和最终的收尾长度来跑。如果只是允许范围变了、checker 逻辑没变，不必重做旧的变异测试；如果运行入口、配置解析、checker 或向量有相关修改，就要对受影响的部分重新验证。开发阶段在 L=3 下的记录要标为"开发自检"，不能混入最终候选的合格结果。

## 4. 分析配置

### 4.1 环境与工具

- 每次运行之前先执行 `env/snapshot.sh check`，失败就停止。
- 工具版本见 `env/INSTALL_RECORD.md`。OpenSTA 每次都用独立的新进程运行：`sta -no_init -no_splash -exit <脚本>`，不继承交互式配置。

### 4.2 综合配方

- 使用 CASE-01 专用的 `tasks/CASE-01/scripts/synth_case01.tcl`。**配方由这个脚本的全部命令和它的 sha256 来定义**，每次运行都记录 sha256。它派生自 `env/sky130hd_kit/synth.tcl`（sha256 记录在 `env/SHA256SUMS`），和 kit 流程相比有两点不同：
  1. `synth -top <TOP> -noabc`：跳过 `synth` 内置的那次通用 ABC 调用；
  2. Liberty 映射使用一个完整的自定义序列 `strash; dc2; &get -n; &dch -f; &nf; &put`，替换掉默认的整个优化序列。新序列不执行显式的 `&fraig` 和 `scorr`，同时也省略了默认序列中的其他步骤和表示转换，包括第一个 `&get -n`、`dretime` 和第二个 `strash`。因此不能把它描述成"只删了两条命令"的单变量实验。

  其余步骤与 kit 脚本相同：用 `tt_025C_1v80` 库映射，dont_use 清单来自 `synth_excluded.cells`，两个文件的 sha256 都记录在 `env/sky130hd_kit/MANIFEST.txt`；最后执行 `setundef -zero`、`hilomap` 和 `write_verilog -noattr -noexpr`。设置了 `SYNTH_LIB` 时，脚本直接报错。kit 脚本本身不修改，冒烟测试也不受影响。
- **选择过程（v1.1，v1.2 补充）**：这次是 F0 之后、F1 校准冻结和阶段 B 候选修改之前的一次显式配方修订。选择的依据，是基线准备阶段已经看到的运行耗时、面积和有限的功能验证结果；所有成功、失败和超时的尝试都保留在 `evidence/F0_v1.1_synth_recipe.md` 及其归档目录里，其中也如实记录了一次 STA 基础设施测试。所以这不是没有接触结果的盲选，也不是阶段 B 的 RTL 优化成果。修订之后，基线和所有候选都使用同一个冻结的配方；不得根据候选的改善或退化再去选择配方。结论只适用于这个已经披露的配方和固定的分析模型。
- **耗时原因（有限结论）**：在当时记录的机器负载下，kit 配方综合 N=16 基线两次分别用了 4572 秒和 4230 秒，统计显示约 99% 的时间花在 ABC 调用上。结合默认命令序列、组合 SAT 扫描的算法性质，以及简化配方的实测结果，判断显式的 `&fraig` 是主要的瓶颈候选；但这次没有分别记录每条 ABC 子命令的耗时，所以不把全部加速都精确归因于它。专用配方综合只要几秒，面积比 kit 配方大约 0.7%；两者的时序差异未知。
- **`scorr`**：这个配方交给 ABC 的是不含寄存器的组合网络，`scorr` 在这种网络上会直接返回，不做时序信号对应，所以去掉它不会损失这次调用中的时序优化。这个结论不适用于将来启用 `-dff`/`-clk` 或其他带时序网络的 ABC 流程。
- 只能通过 `TOP`、`RTL`、`OUT` 这三个环境变量传参；`SYNTH_LIB` 必须未设置，由 grader 检查。
- 每一次有效评估，为一个实现生成一份综合网表。门级功能仿真和所有 scene 的 STA 都用这一份产物，并核对哈希；不为不同的 scene 或不同的验证环节另选网表。重试、复现以及评估修订之后的重新运行，都另建一个 run 目录，旧记录保留。
- 表述上的限制：这个配方没有显式的时钟目标，也没有 IO 驱动或负载目标，并且不包含物理层面的时序修复；与 Yosys 默认的 ABC 脚本相比，它少了 SAT 扫描（`&fraig`）这一步冗余消除。不能笼统地说 Yosys/ABC 完全不做延迟导向的映射，也不能把结果说成"Yosys 默认流程的结果"。

### 4.3 SDC

| 项 | 规定 |
|---|---|
| 时钟 | 单一时钟 `clk`，上升沿，周期 T，`waveform = {0, T/2}`，不传播时钟。source latency、network latency、setup/hold uncertainty、rise/fall clock transition 全部取 0。这是理想时钟模型下的简化 |
| 输入约束对象 | `in_a`、`in_b` 的全部位，以及 `in_valid`、`rst`；不包括 `clk` |
| input delay | 相对 `clk` 上升沿，max = 0.2·T，min = 0，rise 和 fall 都适用 |
| 输入驱动 | `sky130_fd_sc_hd__buf_2`，弧 A→X；驱动单元输入端的 rise/fall transition 显式写为 0 ns（不写时的默认值也是 0，合同要求写明）；每个 scene 采用对应库的模型。不再另用 `set_input_transition` 覆盖输入端口的 slew |
| 输出约束对象 | `out_data` 的全部位，以及 `out_valid` |
| output delay | 相对 `clk` 上升沿，max = 0.2·T，min = 0（即假设外部的 hold 需求为 0） |
| 输出负载 | 每个输出位都接同一个固定外部电容 C_load。C_load 取自指定哈希的 tt_025C_1v80 库中 `sky130_fd_sc_hd__buf_4` 引脚 A 的 `capacitance` 字段，单位 pF。在所有 scene 和所有实现之间都相同；内部单元的引脚电容仍按各 scene 自己的模型。2026-10-06 预读到的值是 0.0024 pF。第一次校准 STA 之前按记录的方法提取，F1 时复核并冻结，见第 9 节 |
| 寄生 | 不读 SPEF，不设 wire-load，不建互连 RC。仍然计入内部接收端的引脚电容、外部 `set_load`，以及它们对单元延迟的影响 |
| 禁止项 | 不加 false path、multicycle、disable timing、额外的 max/min delay，也不按 `rst`/`valid` 做 case analysis。同步复位 `rst` 保留正常的输入时序检查 |

**执行顺序（v1.2 补充，见 TOOL-012）**：对冻结的 OpenSTA 版本，执行顺序为：读入本次需要的全部 Liberty → 读网表并 link → 建立本次需要的全部 scene → 在对应的 mode 中执行完整的 SDC → 核对约束是否生效 → 出报告。不得在最后一次 `define_scene` 之前施加最终的 `set_load`：在这个版本里，建 scene 会清掉已经设置的端口外部负载。之后如果又新增或重建 scene，必须重新施加相应的 SDC 并重新核对。std 和 sweep 在同一个进程里跑时，所有需要的 scene 都要在施加最终 SDC 之前建好。

**负载核对**：逐位核对全部输出位实际生效的外部负载，min 和 max 都要核对。用 `sta::port_ext_pin_cap` 这类返回内部单位的查询时，要明确做 F 与 pF 的换算，并采用合理的浮点容差。`check_setup` 通过、命令执行没报错、或者 SDC 源文件里写了，都不能代替这项核对。负载为 0 或与冻结值不符时，这次 STA 无效，不参与校准，也不参与对比。

示意写法如下。2026-10-06 已在 OpenSTA 7a034b56 上用冒烟网表核验过语法；但当时采用的是"SDC 在前"的顺序，也没有逐个端口查询负载，所以那次核验不能证明 `set_load` 生效了。2026-10-08 已按上面的顺序核验过负载确实生效（TOOL-012）。正式文件在 F1 冻结，以展开后的约束记录为准。

```tcl
create_clock -name clk -period $T -waveform [list 0 [expr {$T/2.0}]] [get_ports clk]
set_clock_uncertainty -setup 0 [get_clocks clk]
set_clock_uncertainty -hold  0 [get_clocks clk]
set_clock_transition 0 [get_clocks clk]
set ins  [get_ports {in_a[*] in_b[*] in_valid rst}]
set outs [get_ports {out_data[*] out_valid}]
set_input_delay  -clock clk -max [expr {0.2*$T}] $ins
set_input_delay  -clock clk -min 0 $ins
set_driving_cell -lib_cell sky130_fd_sc_hd__buf_2 -from_pin A -pin X \
                 -input_transition_rise 0 -input_transition_fall 0 $ins
set_output_delay -clock clk -max [expr {0.2*$T}] $outs
set_output_delay -clock clk -min 0 $outs
set_load $C_load $outs
```

### 4.4 Corner 与报告

- scene 用 `corners.tcl` 建立。正文只用 `std` 组 6 个点，附录用 `sweep` 组 10 个点。
- 每次报告都要给出：6 个点各自的最小 setup slack 和最小 hold slack，以及全局最差值和它所在的 corner；setup 和 hold 的最差 corner 分别找。还要分别给出各类路径的结果：输入到寄存器、寄存器到寄存器、寄存器到输出。某类路径不存在时，标为"不适用"，不能当作 slack 为 0。
- slack 一律用真实值（`worst_slack`），不用全部通过时被截成 0 的 WNS。
- hold 数字标为"理想时钟、综合后模型下的最小 hold slack"，只作为早期观察，不设 hold 修复目标。
- 结论一律限定为"固定模型下、这六个已检查 PVT 点中的结果"。不写 signoff，也不写"签核"。

### 4.5 每次运行的有效性检查

- **约束合理性检查**：`check_setup -verbose` 是必要的结构和约束合理性检查，**它返回 1 表示没有警告**，调用层要把这个结果正确地转换成进程退出状态。但它只检查约束是否存在，不能代替对有效约束的逐项核对。
- **约束逐项核对**：根据展开后的约束记录，逐位核对输入和输出对象、参考时钟、rise/fall 各自的 min/max 项及其数值，并核对驱动和负载。N=16 时，非时钟输入集合应包含 130 位（`in_a` 64 + `in_b` 64 + `in_valid` + `rst`），输出集合应包含 33 位（`out_data` 32 + `out_valid`）；名称和方向都要符合接口，不能只核对总数。
- **scene 绑定**：记录并核对每个 scene 的名称、mode，以及 min/max 各自绑定的 Liberty，确认所有目标 scene 共享本次已检查过的那套 SDC。共享同一个 mode 时，对这个 mode 执行一次 `check_setup` 即可（它没有 `-scene` 参数）；但每个 scene 的库链接、有效结果以及 setup/hold 数值，仍然要分别检查。scene 名称正确，不等于它绑定的库和 SDC 就正确。
- **结果有效性**：全局必需的结果、实际存在的各类路径的报告，以及"查询对象应当存在、却返回空"的情况，都要检查。结果缺失、查询失败、slack 不是有限数，都判失败。某一类路径经过拓扑和对象检查，确认确实不存在时，输出一条明确的"不适用"记录，不生成假的 slack，也不按"缺少报告"判失败。不能把单纯的空查询直接解释为"不适用"。
- CASE-01 的数据路径必须全部受约束。不能只凭工具退出码和一个 slack 数值就判通过。

### 4.6 诊断与比较时的表述规则

- 输入驱动、扇出和负载可能主导本模型下的最差路径。分析原因时，要用报告把外部驱动的贡献、单元逻辑延迟、控制信号扇出和综合配方的影响区分开。本流程不含布局、CTS、布线和物理修复，所以不能看到高扇出就先认定是 RTL 的缺陷，也不能宣称物理工具一定能轻易修好。
- 在冻结的 L 上限之内，允许增加输入寄存器或内部流水寄存器。端口的 input/output delay、驱动、负载和其他分析配置都保持不变。
- 如果改善涉及"长组合段从 IO 预算改为完整周期预算"，必须单独说明。未经控制变量的核验，不给出精确的收益百分比分摊。
- 在约束值不变的前提下，RTL 降低了输入扇出所带来的收益，仍然是本模型内的真实收益；但不能自动归结为算术逻辑深度下降，也不能外推到物理实现。
- 每次对照都同时报告：L、吞吐、面积、6 个点内的全局最差 setup 和 hold，以及第 4.4 节列出的各类路径结果。

## 5. 校准（F0 之后、AI 修改之前）

1. 用 L=1 的基线，通过功能检查后，按冻结的综合配方生成一份网表。本阶段只改变 STA 的试探周期 T，以及随 T 变化的 waveform 和 IO max delay；不重复改变综合策略。
2. 在试探周期 T0 下，检查 6 个 std scene 的约束覆盖和报告完整性。保存每个 scene 的真实最小 setup slack，以及最差路径的类别、端点、corner、arrival 和 required。
3. 如果已经确认主导路径符合 S = 0.8T − D_eff 的形式，就用 D_eff = 0.8·T0 − S0 和 r = 0.15 算出候选周期 T = D_eff / (0.8 + r)。其中 S0 = min_c S_c(T0)，c 遍历 std 组的 6 个点。候选周期按最接近的 0.01 ns 舍入。这只是试探值，舍入之后仍以第 4 步的 6 点实测为准。
4. 在这个 T 下重跑全部 6 个点，用实际的 S = min(S_c) 检查是否满足 −0.20 ≤ S/T ≤ −0.10。如果不满足，就保持网表和其他模型不变，继续搜索周期，并保存所有试探记录。不得通过修改驱动、删掉 corner 或漏掉约束来让它满足。如果第 3 步的公式前提不成立，直接用同样的固定模型做周期搜索。
5. 只有实测满足区间要求、并且覆盖检查通过之后，才进入 F1。达不到时记录失败原因，按企划 R2 第 4 条和第 8 节的修订流程处理；不能把公式预测值当作已经通过。

"只做一次"指的是 AI 修改之前只有一个校准阶段，其中可以包含多次 T 的试探。同时保存 6 个点各自的最小 hold slack，只作为观察。

## 6. grader 与运行记录

- 环境快照核对失败，立即停止。
- **以下情况都使该次评估无效，并返回非 0**：任何一个工具失败；STA 报 Error；出现不在本次适用、已审阅的窄范围白名单内的 Warning；对象匹配错误；漏约束；缺少必需的报告；出现不合法的数值。单独写一段解释，不能让某个 Warning 自动获得被忽略的资格。
- **仿真结果由 grader 独立判定**：grader 分别检查本次运行新产生的 RTL 仿真日志和门级功能仿真日志。每一份都必须同时满足：进程退出码为 0；没有失败记录；恰好有一行完整匹配 `SIM PASS checked=<n>`；n 是正整数，并且等于对应清单里 Python 给出的期望数；适用的覆盖要求都通过。不能只搜索 PASS 子串，也不能只相信 TB 自己宣告通过。两个仿真的计数要分别核对，不能相加之后再和 Python 的总数比较。
- 如果确实有可以接受的非致命 Warning，只能在 F1 之前，按具体的消息内容和出现条件，列出一个范围很窄的白名单并说明理由；完整日志照样保存。不得全局忽略 Warning。
- 三种状态分开记录：功能通过、分析执行有效、达到预定的时序目标。基线本来就预期有负 slack，候选也可能没有改善，这两种情况都不是工具报错，但也不能标成"优化成功"。
- 每次运行都放在单独的 `runs/<run_id>/` 目录下，不覆盖旧的。目录里保存：实际使用的 RTL、cfg、向量和种子、参考模型、TB、SDC、脚本，综合网表的哈希，门级仿真所用两个模型文件的哈希，库和工具的标识或哈希，完整日志，以及每一步的退出状态。注意：环境快照核对通过，并不能证明这次运行用的 cfg、SDC 和 RTL 是对的，这些要单独保存和核对。

## 8. 冻结与修订

- **F0**：在开发 RTL 和 TB 之前冻结。冻结的内容是接口、功能、采样和复位语义、验证要求、分析配方和校准规则。T、C_load、L_max、资源上限、Warning 白名单这几项，按第 9 节的约定留到 F1 再填。F0 之后，如果要改变已经冻结的条款，必须做显式修订；按 R2 回退到 8 位就属于这种修订。

## 10. 本模型的局限（写进报告和文章）

- 布局前分析，理想时钟；只计引脚电容，没有互连寄生。
- 输入驱动单元的输入 transition 取 0 ns，这是简化，不代表真实的板级或芯片接口。
- 综合配方没有时钟目标和 IO 目标，也没有物理修复步骤；它使用 CASE-01 专用的 ABC 序列，不执行显式的 `&fraig` 和 `scorr`（第 4.2 节）。
- 本实验没有证明 RTL 改善在 Yosys 默认配方或其他综合流程下依然成立。如果某个修改主要是通过消除冗余取得收益，默认流程可能会自动消除同样的冗余，也可能得到不同的映射；没有做配对对照时，不得断言默认流程一定能、或一定不能取得同样的收益。结果只表示这个 RTL 修改在已冻结的 CASE-01 专用配方下的效果，不表示 AI 超越了默认综合器的优化能力。
- 所有结论都限定在固定模型下、六个已检查的 PVT 点之内，不外推到硅片上的频率、布线后的收敛或 signoff。
